# Архитектура эталонной ноды

[English](architecture.md) · **Русский** · [中文](architecture_zh.md)

ПО 1.0.32. Протокол 1.0 (loft/1.0). Протокол: [protocol_ru.md](protocol_ru.md). Эксплуатация: [guide_ru.md](guide_ru.md). Если вы впервые читаете код: [code-tour_ru.md](code-tour_ru.md).

Документ описывает дерево на Go в этом репозитории. Сторонняя реализация **может** раскладывать код по каталогам иначе и при этом говорить по протоколу.

---

## 1. Кратко

Эталонная нода — один двоичный файл `loft-node`, который работает в двух ролях: контроллер и relay. Эталонный клиент — `loft` (CLI: SOCKS5 и, по желанию, TUN). `loft-front` поднимает ту же сессию без флагов CLI, для системных маршрутов; приложение macOS в строке меню запускает его как помощник. `loft-probe` проверяет ICMP/TCP/UDP/DNS/HTTP через сессию. Общий код лежит в `internal/`.

## 3. Сессия

Сессия участника складывается из соединения, auth blob и Status, после чего идёт mux.

```
client.Holder
    Supervise(cfg)                 перебирает исходящие и фронты
        Open(target)               get | ws | h2 | quic | h3 | l3
            TLS 1.3 (uTLS)
            auth 0x02 (nonce || eph_c || HMAC)
            Hello MemberCaps (без CapRelay; ExtraCaps у loft-node relay)
            eph_n || AEAD(Status)
            mux Open / Data / Close / Dgram / Leave
```

`Supervise` предпочитает GET. После Status непустой `ticket` служит идентификатором сессии. Поле Status `fronts` перечисляет точки подключения mux (имя, путь, необязательный URL), которые принимает нода; клиент присоединяется по этим путям, и ему СЛЕДУЕТ переписать сохранённый профиль. Клиент МОЖЕТ присоединить `ws` / `h2` / `quic` / `h3` с тегом `0x04` (HMAC от ключа сессии, а не второй `0x02`). GET при этом остаётся. Основной поток mux идёт по присоединённому фронту (`CmdFront`); если тот отвалится, поток возвращается на GET с тем же ключом, mux и seq. `l3` и `connect` не присоединяются.

Если GET-сессии для присоединения нет, `Supervise` при `select: auto` перебирает настроенные исходящие в порядке списка. После первого Status он оставляет только пересечение фронтов. При отказе переходит к следующему оставшемуся фронту, затем к неподписанным `replicas`, затем к подписанному roster. Нода без `fronts` объявляет только GET; `ws`, `h2`, `quic`, `h3` и `l3` перечисляются явно. `l3` — это HTTP/2 CONNECT, за которым идут IP-датаграммы (без mux); TUN просто копирует пакеты и не поднимает TCP-стек в пространстве пользователя.

`WatchPath` проверяет исходящий IPv4-адрес по умолчанию примерно четыре раза в секунду. На GET смена адреса (Wi-Fi / LTE / VPN) заменяет сокеты HTTP/2, а sid, mux и seq сохраняются (без `0x02`). Если присоединённый фронт отваливается, основной поток возвращается на GET без Park. При смене пути на одиночном `ws` / `h2` / `quic` / `h3` (без GET ticket) клиент делает Park и свежий `0x02` с тем же `instance_id`. SOCKS5 и TUN остаются привязаны (`Holder`), IP оверлея не меняется. При возможности `hold` Park держит потоки mux `gap_hold_ms` (по умолчанию 8 с), и внутренний TCP не получает RST. GET-рукопожатие после Park подхватывает этот mux по `instance_id` (новый HTTP sid, тот же mux). Этот цикл крутят и `loft`, и `loft-front`.

Для запроса roster нужен `controller_pub`. `tofu: true` закрепляет первого действительного подписанта и записывает `{instanceDir}/controller.pub`. С пустым ключом и без этого флага roster не принимается, но статические исходящие всё равно подключаются.

Nonce внутреннего AEAD уникален в пределах ключа сессии (32-битный префикс + 64-битный счётчик). Park с тем же ключом продолжает счётчик. Новый `0x02` выводит новый ключ из X25519; ikm для HKDF — общий секрет DH. После Status прямой фронт может работать без внутреннего AEAD или на AES-256-GCM; `get` остаётся на ChaCha20-Poly1305. Seal(Status) при рукопожатии всегда идёт на ChaCha20-Poly1305.

Клиент не выбирает decoy SNI сам: его сообщает Status, roster или сертификат, полученный зондом. Исходящий через CDN сохраняет hostname CDN.

Локальный вход (SOCKS5, TUN) вызывает `Holder.Open(host:port)` или отправляет датаграмму. Адреса оверлея разрешает `NetSwitch` на ноде. Поле Status `dns` — список IP резолверов; нода отвечает на `gateway:53`, используя `dns.upstream` (DoH, DoT или UDP). Если необязательный хвост Status `ip6` / `gateway6` отсутствует, работает только IPv4.

## 4. Роли ноды

### 4.1 Контроллер

Хранит:

- ключи участников в виде SHA-256 в `network.conf`, открытым текстом — в `{dir}/members.keys`. `auth shared enable` принимает `LOFT_TOKEN` как секрет клиента, только пока этот набор ключей пуст.
- аренды и IP оверлея
- ACL и VLAN
- Ed25519 seed `{dir}/controller.seed`
- актуальный roster и списки адресов

Он **может** слушать 443 для участников. Транки relay он слушать **должен**.

Seed для подписи создаётся при первом запуске. Открытый ключ отдаётся клиентам как `controller_pub`. Эталонный клиент не закрепляет неизвестного подписанта, пока не задано `tofu: true`.

### 4.2 Relay

Завершает публичный TLS. Открывает к контроллеру один транк с возможностью `relay` в Hello. Внутри этой сессии:

- `ctl:1` — enrol, beat, slice, drain
- на каждого участника — `hub:1` (HTTP/1.1) или `hub:2` (HTTP/2)

Relay копирует HTTP после TLS в `hub:1` / `hub:2`. Внутренний AEAD mux и FinishAuth остаются на контроллере. Relay не расшифровывает кадры оверлея, не выдаёт аренды и не хранит ключи участников. IP оверлея назначает контроллер.

IP relay может меняться. Снятие relay из roster увеличивает serial. Клиенты, уже получившие Status, держат сессию до отказа, а затем берут новый roster.

### 4.3 Origin

`server/origin` — HTTPS-приложение, которое обслуживает публичный путь:

- страница прикрытия (`cover_dir` или встроенная страница)
- GET-фронт, WebSocket, HTTP/2 CONNECT
- публичный roster и JSON со списками

Зонд, ушедший в стыковку с decoy, до этого обработчика не доходит: его пересылают на настроенный origin ещё до уровня HTTP.

### 4.4 Хост Debian

Unit systemd, установщик и `.deb`: [server/debian/README_ru.md](../server/debian/README_ru.md). Токен лежит в `/etc/loft/loft.env`, документ оверлея — в `/var/lib/loft`. Процесс работает от пользователя `loft` и слушает 443 благодаря `CAP_NET_BIND_SERVICE`.

## 5. Decoy и mask

`transport.WrapDecoy` заглядывает в TCP ClientHello.

```
Accept
  read ClientHello (или оставшиеся байты)
  if valid session_id and own SNI
      сертификат ноды (участник на advertise, CDN после sid)
  else if own SNI from cdn_peers
      сертификат ноды (CDN origin pull)
  else if session_id = sid v3, или sid v2 пока mask выключен
      if mask ready → лист ECDSA формы dest + выравнивание записей
      else            → обработчик HTTP loft
  else
      TCP-стыковка с decoy origin (совпадение SNI, иначе основной)
UDP
  decoy on → стыковка датаграмм с dest
  decoy off → loft QUIC/H3
```

С чем стыковать, задаётся в конфигурации ноды, и клиент это узнаёт. Имена хостов в YAML — примеры, а не константы протокола.

Mask выпускает лист ECDSA P-256 с идентичностью origin и подписывает CertificateVerify как `ecdsa_secp256r1_sha256`. Серийный номер привязан к ECDH с X25519 ноды. Если ClientHello предлагает X25519MLKEM768 (`0x11EC`), ServerHello выбирает эту группу; лист остаётся вне WebPKI. На собственном SNI sid v2 по-прежнему принимается, и клиент видит сертификат ноды. Зонды, sid v2 на SNI приманки и повтор TCP `client_random` в течение 10 минут уходят в стыковку. На ноде с mask Initial QUIC принимается только с меткой v3. Записи приложения **могут** повторять длины ciphertext у origin.

## 6. Связность оверлея

`transport.Overlay` привязывает каждую допущенную сессию к IP оверлея. Open на адрес внутри CIDR сети классифицируется по `peers`:

| режим | действие |
|------|----------|
| hub | Reset `policy_drop` |
| mesh | стыковка с mux-сессией пира как Open `127.0.0.1:port` |
| vlan | mesh, если VLAN совпадает |

TCP Open и ICMP оверлея проходят через `Network.Allow` (теги, CIDR, VLAN, `default deny`). `ip route DST VIA|member ID|tag NAME` задаёт CIDR за участником: Open `host:port` стыкуется с этим участником с исходным target. Поле Status `routes` перечисляет эти CIDR с уже разрешённым overlay IP; самого владельца VIA в списке нет. Open в интернет (вне CIDR и этих маршрутов) не меняется. Прямой P2P использует Status `policy` и тот же Allow. `session ttl_ms` закрывает живую сессию; `lease_hold_ms` держит overlay IP после обрыва.

Принимающий клиент принимает Open и открывает target. При стыковке по overlay IP это `127.0.0.1:port`, при маршрутизации — `host:port` на стеке хоста участника.

Необязательный P2P: клиент слушает порт и объявляет `loft.peer:<port>` и 32-байтный открытый ключ X25519, а Status передаёт хост, увиденный при TLS, порт и ключ. Прямой TCP начинается с шифрованного рукопожатия (свежие ключи X25519, доказательство на ECDH пары с ключом пира, случайное дополнение, без фиксированных байт), а данные идут под ChaCha20-Poly1305 (`p2pseal.go`); затем действует тот же ACL, что и при стыковке через хаб, если Status несёт policy. При отказе используется стыковка через хаб. С `p2p: false` клиент не слушает порт. Seed: `{instanceDir}/p2p.seed`.

## 7. Списки адресов

Контроллер публикует именованные множества. Клиент сопоставляет имена с действиями (`use:`). Если совпадений несколько, приоритет такой: drop, затем direct, затем via. Для назначений без совпадений по умолчанию — `via`.

SOCKS сопоставляет hostname из запроса, TUN — IP назначения по CIDR. Доменные правила к сокетам с сырыми IP не применяются.

Списки запрашиваются, когда Status `lists_serial` или `lists_hash` новее кэша. Подпись — тот же Ed25519, что и у roster.

## 8. Локальный вход

| слушатель | по умолчанию | заметки |
|-----------|--------------|---------|
| SOCKS5 | `127.0.0.1:1080` (GUI / `client.yaml`); `127.0.0.1:18080` (`loft` / `loft-front`, если порт не задан) | RFC 1928. CONNECT и UDP ASSOCIATE, когда включён `dgram`. |
| TUN | выкл; `tun: auto` создаёт utun | стек gVisor в пространстве пользователя. UDP через CmdDgram. ICMP echo: на себя — локально; в оверлей и интернет — как Dgram `:1` (нода отправляет настоящий ICMP echo). Darwin для ICMP транслирует фиктивный `169.254.8.1` ↔ IP оверлея. |
| kill-switch | `listen.kill_switch` | когда последний TUN умирает, системный маршрут по умолчанию остаётся снятым, пока пользователь его не вернёт |

TUN исключает исходящие хосты сессии loft (CDN, нода), чтобы туннель не проглотил собственный путь.

Клиент macOS в строке меню написан на Swift 5 + AppKit: [`clients/macOS/Sources/`](../clients/macOS/Sources/). UX: [`clients/macOS/design/DESIGN_ru.md`](../clients/macOS/design/DESIGN_ru.md). Живую сессию держит `loft-front` из бандла (`Contents/MacOS/loft-front`), а не тип `GETFront.swift` внутри процесса. Hello этого помощника отправляет клиент на Go (GET и WS). Удержание маршрута, запасной путь и раздельные списки из дизайн-документа — политика уровня машины; она работает поверх флагов CLI на Go.

## 9. Запасной путь

Порядок попыток после гибели сессии:

1. GET ещё жив, а присоединённый фронт умер: основной поток возвращается на GET (тот же ticket, без `0x02`).
2. Оставшиеся фронты из пересечения на том же исходящем.
3. Следующий исходящий в порядке `select: auto`.
4. Неподписанные `replicas` из Status.
5. Подписанные записи roster с учётом веса, минуя те, что в drain.

Таймеры переподключения приходят из Status: `reconnect_min_ms`, `reconnect_max_ms`, `reconnect_fast_n`, `reconnect_fast_for_ms`. Сначала идут быстрые попытки, затем экспоненциальная пауза.

Реплика принимает свежий `0x02`. Hello `instance_id` сохраняет аренду в оверлее.

Mux `Pull` сначала выбирает Open/Ping/Pong/Dgram/Leave и мелкие Data (≤ 4 КиБ), а уже потом основные Data/Pad, чтобы большая загрузка не тормозила ICMP, TCP ACK и loaded-ping Cloudflare. Close/Reset остаются в очереди Data, чтобы штатное закрытие не обогнало оставшиеся байты. Очередь Data — 48 кадров. Предвыборка WS — 2×48 КиБ; управляющие кадры идут отдельным сообщением на 8 КиБ.

`session rate_bps` (значение по умолчанию для сети, переопределяется через `config member ID rate_bps`) — token bucket на основной трафик `CmdData`/`CmdDgram` сессии участника в обоих направлениях. 0 — выключено. Управляющие и мелкие кадры не ограничиваются. Поле Status `rate_bps` объявляет потолок, а соблюдает его нода. Транки relay не ограничиваются.

## 10. Параллельность

Одна mux-сессия на экземпляр участника. Потоки — это горутины с ограниченным приёмным буфером. Полезная нагрузка mux ≤ 16384; `Stream.Write` и `EncodeBatch` дробят CmdData, чтобы `io.Copy` блоками по 32 КиБ не терял кадр.

У GET-фронта ограниченное окно одновременных запросов (по протоколу 2–8, по умолчанию 4; в этом дереве по умолчанию 8). Цикл клиента — единственный Puller исходящего канала, он присваивает GET `seq` в порядке Pull. Нода применяет исходящие данные по порядку seq; входящий mux вытягивает только очередной по порядку GET, чтобы потерянный HTTP-ответ не унёс кадры, уже взятые из mux (YouTube/Speedtest TLS). Интервал GET в простое — `keepalive_ms / 2` (не меньше 1 с) с разбросом ±⅓. Open и крошечные Data ждут 15 мс, датаграммы — 80 мс, чтобы ICMP уехал в том же теле. Общий GET `header_budget` в этом дереве — 16 КиБ HTTP-заголовка (декодированный mux — ~12 КиБ после base64url+AEAD, ~13 КиБ после Cookie Z85); профиль Yandex фиксирует 16 КиБ в закодированном виде. Status `h2_conns` (на ноде `get_h2`, 1–4) — дополнительные HTTP/2-соединения, дающие второй бюджет заголовков; inflight при этом считается суммарно. Необязательный клиентский `h2_max_age_ms` (0 — держать до ошибки) заменяет это TCP-соединение, а mux и GET sid сохраняются. Смена локального исходящего адреса так же заменяет пул HTTP/2 (без нового `0x02`). GET, у которого в исходящем канале уже ≥ 2 КиБ CmdData, ограничивает тело 96 КиБ, чтобы слот Cookie освобождался быстрее; при чистом скачивании лимит остаётся 256 КиБ.

Транки relay — одна mux-сессия на процесс relay со множеством потоков `hub:*`.

`Supervise` — один цикл на клиентский процесс. Несколько YAML-профилей (несколько профилей в macOS) — это несколько процессов или несколько Holder, а не возможность `multi`. Возможность `multi` — это несколько значений `instance_id` на одном ключе участника.

## 11. Что находится в других местах

Виртуальные машины, публичный DNS, публичные сертификаты и обновление двоичных файлов находятся вне этого протокола. Unit systemd, POSIX-установщик и `.deb` лежат в [`server/debian/`](../server/debian/). По каналу передаются enrol, beat, slice, drain, roster и списки. Оператор выдаёт ключи участникам и пишет `network.conf` и `members.keys`.
