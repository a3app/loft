# Yandex Cloud CDN для loft

[English](../README.md) · **Русский** · [中文](yandex-cdn_zh.md)

Инструкция для оператора: что нажимать в консоли Yandex Cloud, чтобы GET-фронт loft шёл через Cloud CDN.

Профиль `cdn: yandex` в клиенте — не возможность (capability) протокола. В канале по-прежнему используется фронт `get`. Имя Yandex в YAML лишь ужимает бюджет заголовков и задаёт SNI.

Через этот край проходит **только GET**. На POST и WebSocket край отвечает 405, на GET с телом — 413. Одиночный запрос пропускает Cookie до ~40 КиБ, но 16 параллельных запросов с такими заголовками край обрывает (HTTP/2 GOAWAY `ENHANCE_YOUR_CALM`), поэтому бюджет заголовка — 16 КиБ. Источник обязан ответить за 5 секунд. К origin CDN обращается только по IPv4.

Скриншоты сделаны в консоли Cloud CDN (каталог `default`). В примерах origin — `loft.example.com`, раздача — `cdn.example.com`. Подписи на экране совпадают с таблицами.

---

## Имена в примерах

Подставьте свои. В примерах используются такие:

| Роль | Значение |
|------|----------|
| Origin (нода) | `loft.example.com:444` — `advertise https://loft.example.com`, сертификат ноды `CN=loft.example.com` |
| CDN-ресурс | `cdn.example.com` |
| CNAME раздачи | `cdn.example.com` → `<id>.topology.gslb.yccdn.ru` |
| ACME | `_acme-challenge.cdn.example.com` → `<цель из карточки>.cm.yandexcloud.net` |
| GET path | `/static/v3/build` (по умолчанию на ноде, если `get_path` в `node.conf` пуст) |
| Группа источников | `loft-origin` |
| Панель | `#loft/node` — поле **Сертификат ноды** |

Токены и ключи участников в консоль CDN не попадают. Они остаются в `{dir}/members.keys` и в YAML клиента.

## 1. Origin — нода loft, до консоли

CDN открывает к ноде **собственное** TLS-соединение. HMAC из ClientHello клиента до ноды не доходит. Поэтому сессия живёт на уровне HTTP: в первом GET идёт Cookie `session=` с тегом `0x02`, а идентификатор сессии уже стоит в пути; дальше тоже Cookie `session=` (AEAD). `X-Session` нода по-прежнему ставит, но новому клиенту он не нужен.

Значит, origin для CDN — это слушатель, который **сам** отвечает на `GET` по `get_path`, а не стыкует чужой ClientHello с decoy.

На ноде:

```yaml
listen: ":444"
advertise: https://loft.example.com
get_path: /static/v3/build   # тот же path, что у клиента
get_h2: 2                   # второй HTTP/2 к CDN; inflight общий. 1 = как раньше
fronts: [get]               # ws/h2/quic на этом слушателе CDN не пронесёт
# decoy/mask можно оставить: ребро ходит с SNI advertise (loft.example.com),
# без session_id — нода отвечает своим сертификатом, не сплайсирует.
# Чужой SNI по-прежнему уходит в decoy. Host и SNI у CDN — loft.example.com.
```

Сертификат ноды должен покрывать Host/SNI, с которыми CDN обращается к origin; в примерах это `loft.example.com`. В панели: `#loft/node` → **Сертификат ноды** → пара из пула на это имя → Сохранить. Пути в `node.conf` остаются прежними: `/etc/loft/tls/fullchain.pem` и `privkey.pem`.

Если на ноде стоит сертификат `other.example.net`, а Host у CDN — `loft.example.com`, то ни TLS-клиенты, ни проверка origin со стороны CDN не пройдут.

Проверьте origin напрямую, минуя CDN. SNI должен быть `loft.example.com`, иначе при включённом decoy рукопожатие уйдёт в стыковку:

```bash
curl -sI --max-time 5 --resolve loft.example.com:444:ORIGIN_IPV4 \
  https://loft.example.com:444/static/v3/build
```

Ожидается ответ самой ноды (cover или 404 на голый path без сессии), а не страница decoy и не обрыв по таймауту.

Файрвол origin должен пропускать IPv4 с адресов Yandex CDN. Origin, доступный только по IPv6, край использовать не сможет.

Соединение клиента с краем и выход ноды в интернет тоже идут по IPv4 (`tcp4`). Пока IPv6 в оверлее не выдан, DNS-заглушка отвечает на AAAA пустым NOERROR, иначе Happy Eyeballs уведёт трафик в нативный IPv6 ноды.

Нода уже ставит на ответы GET `Cache-Control: private, no-store`, `CDN-Cache-Control: no-store`, `Vary: Cookie`. Этого недостаточно: кэш на **ресурсе CDN** всё равно нужно выключить (шаг 2 мастера).

Nginx перед GET-фронтом loft на `:444` не нужен: нода сама служит origin. Если на той же машине nginx слушает 80/443 (другие сайты), loft-node вешается на `:444`, и край забирает данные с origin именно с `:444`. Nginx, как в гайдах по Xray (шаг 7), на этом пути не стоит; если поставить его перед GET, он добавит буферизацию, `proxy_read_timeout` и обрезание `Cookie`/`X-Session`.

## 2. Платёжный аккаунт

Оплата Cloud CDN списывается с **платёжного аккаунта**. Он идентифицирует плательщика и привязан к лицевому счёту, но ресурсами (каталог, CDN) не управляет.

Консоль: [Yandex Cloud Billing](https://console.yandex.cloud/billing) → вкладка **Аккаунт** → **Создать аккаунт**.

Официальная документация: [создать новый платежный аккаунт](https://yandex.cloud/ru/docs/billing/operations/create-new-account).

1. Войдите с Яндекс ID или аккаунтом Яндекс 360.
2. Если организации ещё нет, создайте её в [Identity Hub](https://console.yandex.cloud). В ней появится каталог `default`.
3. Откройте сервис **Yandex Cloud Billing**.
4. На вкладке **Аккаунт** нажмите **Создать аккаунт**. Второй и последующие аккаунты создаются кнопкой «плюс» рядом с именем текущего.
5. В окне создания:
   - **Имя аккаунта** — под этим именем аккаунт будет виден в списке.
   - **Организация** — та, в которой вы будете создавать CDN.
   - **Тип аккаунта** — **Физическое лицо** или бизнес-аккаунт (ИП / юрлицо). После создания тип не меняется.
   - **Страна** — резидентство плательщика. В рамках одного Яндекс ID все плательщики платят в одной валюте.
   - **Способ оплаты** — банковская карта или пополнение вручную.
6. На странице аккаунта в блоке **Привязанные облака и сервисы** должно быть облако, привязанное к этому платёжному аккаунту. Без привязки облако неактивно, и создать в нём Cloud CDN нельзя.

Для создания аккаунта нужна роль владельца организации. На странице Billing статус должен быть «активен» или «пробный период»; сам Cloud CDN создаётся уже в [консоли управления](https://console.yandex.cloud), в каталоге этого облака.

## 3. Группа источников

Навигация: `Cloud CDN / Группы источников / Создать`. Заголовок — **Создание группы источников**. Сертификата на этой форме нет, только origin.

![Форма «Создание группы источников»: тип Сервер, одно поле «Доменное имя источника»](img/yandex-cdn/01-origin-group.jpg)

| Поле на экране | Что писать |
|----------------|------------|
| **Название группы** | `loft-origin` |
| **Тип источника** | **Сервер** (не Бакет и не L7-балансировщик) |
| **Доменное имя источника** | `loft.example.com:444` |
| **Приоритет** | **Основной** |

**Добавить источник** не нажимайте. Нажмите синюю кнопку **Создать**.

CLI:

```bash
yc cdn origin-group create --name loft-origin \
  --origin source=loft.example.com:444,enabled=true \
  --provider-type ourcdn
```

Запомните `id` группы.

Документация: [создать группу источников](https://yandex.cloud/ru/docs/cdn/operations/origin-groups/create-group).

## 4. CDN-ресурс

Навигация: `Cloud CDN / CDN-ресурсы / Создать`. Откроется мастер, **Шаг 1 из 4 — Основные настройки**.

### Шаг 1. Основные настройки (блок Контент)

По умолчанию вверху формы выбрано **Из одного источника**. Нужна уже созданная группа:

![Шаг 1: блок Контент. Переключить «Запрос контента» на «Из группы источников»](img/yandex-cdn/02-resource-step1.jpg)

| Поле на экране | Что выбрать / писать |
|----------------|----------------------|
| **Доступ к контенту** | флажок установлен |
| **Запрос контента** | **Из группы источников** (группа `loft-origin`) |
| **Тип источника** / **Доменное имя источника** | не нужны, если выбрана группа |
| **Протокол для источников** | **HTTPS** |
| **Задать SNI вручную** | **включить**, значение — `loft.example.com` (без порта) |
| **Заголовок Host** | **Свое значение** |
| **Значение заголовка** | `loft.example.com` |
| **Доменное имя** | `cdn.example.com` (ваше имя раздачи). После создания его нельзя изменить |
| **Метки** | пусто |

Нижняя половина того же шага — Host и имя раздачи:

![Host = loft.example.com, протокол HTTPS, группа loft-origin. Доменное имя — cdn.example.com](img/yandex-cdn/03-resource-host.png)

На скриншоте переключатель **Задать SNI вручную** выключен. Его нужно включить и указать то же имя, что и в Host: `loft.example.com`. Иначе край придёт к origin с SNI `cdn.example.com`, а сертификат ноды на это имя не выпущен.

### Шаг 2. Кеширование

Так выглядят **настройки по умолчанию**. Для loft они вредны: тело GET зашифровано AEAD, и кэширование или нарезка на крае ломают сессию.

![Дефолт кеша: «Кеширование в CDN» включено, cookie игнорируются, сегментация больших файлов включена — всё это выключить](img/yandex-cdn/04-cache-defaults.jpg)

| Поле на экране | Что поставить |
|----------------|---------------|
| **Кеширование в CDN** | **выключить** (сейчас переключатель синий) |
| **Кеширование в браузере** | выключено — так и оставить |
| **Кеширование query-параметров** | **Не кешировать** |
| **Игнорировать файлы cookie** | **снять** флажок |
| **gzip-сжатие** | выключено |
| **Сегментация больших файлов** | **снять** флажок |

После отключения кеширования в CDN блок «Как у источника / День» исчезает — так и должно быть.

### Шаг 3. HTTP-заголовки и методы

`Cookie` клиент передаёт сам, дублировать его статическим заголовком не нужно. `X-Session` из ответа ноды доходит до клиента, пока выбрано **Не скрывать**; новому клиенту он не нужен.

![Заголовки: ничего не добавлять, скрытие заголовков источника — «Не скрывать», CORS — «Не добавлять»](img/yandex-cdn/05-headers.png)

![Методы: GET, HEAD, OPTIONS. «Настраиваемый HTTP-ответ» выключен](img/yandex-cdn/06-methods.png)

| Поле на экране | Что поставить |
|----------------|---------------|
| **Заголовки запроса к источнику** → **Добавить** | не нажимать |
| **Заголовки ответа клиенту** → **Добавить** | не нажимать |
| **Скрытие заголовков источника** | **Не скрывать** |
| **CORS** / Access-Control-Allow-Origin | **Не добавлять** |
| **Методы запросов от клиентов** | GET, HEAD, OPTIONS |
| **Настраиваемый HTTP-ответ** | выкл |

### Шаг 4. Дополнительно

![Шаг 4: выгрузка логов и экранирование источников выключены. Кнопка «Продолжить»](img/yandex-cdn/07-extra.png)

| Поле на экране | Что поставить |
|----------------|---------------|
| **Выгрузка логов** | выкл |
| **Настройки экранирования** | выкл |

Нажмите **Продолжить**. Настройки применяются в течение 15 минут. После изменения настроек кеширования сбросьте кеш ресурса.

CLI (заготовка):

```bash
yc cdn resource create cdn.example.com \
  --origin-group-id ORIGIN_GROUP_ID \
  --origin-protocol HTTPS \
  --host-header loft.example.com \
  --disable-cache \
  --cert-manager-ssl-cert-id CERT_ID
```

Документация: [создать ресурс](https://yandex.cloud/ru/docs/cdn/operations/resources/create-resource), [заголовки](https://yandex.cloud/ru/docs/cdn/operations/resources/configure-headers), [кэширование](https://yandex.cloud/ru/docs/cdn/concepts/caching).

## 5. DNS и сертификат CDN

Сертификат Let's Encrypt выпускается **на имя раздачи** (`cdn.example.com`), а не на origin (`loft.example.com`). Origin уже защищён сертификатом ноды из панели.

На форме группы источников сертификата нет. Он задаётся в ресурсе, в поле **Тип сертификата**.

Проще всего выпустить его прямо там: **Тип сертификата** → Certificate Manager → выпуск Let's Encrypt на `cdn.example.com`.

Если открывать Certificate Manager отдельно (тот же каталог `default`):

1. В строке навигации нажмите на **домик** (слева от `Cloud CDN`) — это дашборд каталога, а не Cloud CDN.
2. В поиске вверху консоли введите `Certificate Manager`.
3. Сервис **Certificate Manager** → **Добавить сертификат** → **Сертификат от Let's Encrypt**.
4. **Домены:** `cdn.example.com`. Способ проверки прав — DNS. В зоне имени раздачи добавьте запись:

```
_acme-challenge.cdn.example.com.  CNAME  <цель из карточки сертификата>.cm.yandexcloud.net.
```

Цель берётся из карточки сертификата. Certificate Manager видит запись не сразу, нужно подождать.

Когда статус станет «выпущен», выберите этот сертификат в CDN-ресурсе. Пока стоит сертификат по умолчанию `*.yccdn.cloud.yandex.net`, HTTPS на `cdn.example.com` обрывается (SAN mismatch / RST).

Обходной путь, пока сертификат LE не подключён: перевести ресурс в режим только HTTP, а в клиенте указать `url: http://cdn.example.com` (без TLS на крае). К origin при этом всё равно ходят по HTTPS.

После создания ресурса консоль показывает цель вида `….topology.gslb.yccdn.ru`. В DNS:

```
cdn.example.com.  CNAME  <id>.topology.gslb.yccdn.ru.
```

Клиент проверяет этот сертификат (`insecure_skip_verify: false`).

Официальная документация: [добавить сертификат Let's Encrypt](https://yandex.cloud/ru/docs/certificate-manager/operations/managed/cert-create).

## 6. Клиент

`path` исходящего совпадает с `get_path` ноды (`/static/v3/build`). В `url` — схема `https` и имя CDN, без порта origin.

```yaml
listen:
  socks5: 127.0.0.1:18080
select: cdn-get
outbounds:
  - name: cdn-get
    type: get
    cdn: yandex
    url: https://cdn.example.com
    path: /static/v3/build
    fingerprint: chrome
    header_budget: 16384
    inflight: 16
    insecure_skip_verify: false
```

`cdn: yandex` в `internal/cdn/yandex.go` фиксирует бюджет 16 КиБ и inflight 16. Край держит к origin ~10–12 соединений HTTP/1.1: при 32 одновременных GET задержка TTFB для Cookie вырастала до ~900 мс при той же скорости выгрузки ~3 Мбит/с. Явный `header_budget: 16384` — подстраховка на случай, если профиль не применился.

SNI клиента — `cdn.example.com`. Если `cdn` задан, транспорт выставляет его сам.

macOS-клиент `loft-front` пока жёстко задаёт 16 КиБ и `Insecure`. Для проверки края используйте CLI `loft` с YAML выше или `loft-bench -cdn yandex`.

## 7. Проверка

Сначала проверьте cover через CDN (без токена):

```bash
curl -sI --max-time 8 https://cdn.example.com/
curl -sI --max-time 8 https://cdn.example.com/static/v3/build
```

Ожидается ответ ноды со статусом не 502/504. Голый `/static/v3/build` без сессии даёт обычный cover/404 ноды.

Затем проверьте GET-сессию. Без `-path` `loft-bench` идёт на GET-путь по умолчанию, `/static/v3/build`; если у ноды другой `get_path`, укажите его в `-path`:

```bash
make bench
./dist/clients/go/loft-bench \
  -cdn yandex \
  -type get \
  -url https://cdn.example.com \
  -path /static/v3/build \
  -token "$LOFT_TOKEN"
```

`-cdn yandex` включает бюджет 16 КиБ и проверку TLS. WS через этот край не проверяется.

Или через CLI:

```bash
./dist/clients/go/loft -c cdn-client.yaml
ALL_PROXY=socks5://127.0.0.1:18080 curl -sI https://example.com
```

CLI `loft` / `loft-front` без явно заданного порта слушают `127.0.0.1:18080`, чтобы не занимать `1080`, если открыт GUI. YAML — из §6 (`cdn-get` + `listen.socks5: 127.0.0.1:18080`).

## Типичные ответы края

| Симптом | Что проверить |
|---------|----------------|
| GOAWAY `ENHANCE_YOUR_CALM`, потери пакетов | `header_budget` больше 16 КиБ; клиент без `cdn: yandex` |
| 413 | у GET есть тело; клиент без `cdn: yandex` |
| 405 | WS или POST; для Yandex нужен только GET |
| 502 | Host/SNI к origin не совпадают с сертификатом ноды (`other.example.net` не покрывает `loft.example.com`); decoy стыкует запросы края |
| 504 / таймаут origin 5 с | SNI/Host к origin не совпадает с именем advertise (нода уводит в стыковку); файрвол; у origin нет IPv4 |
| Рукопожатие проходит, mux пустой | CDN не пропустил Cookie |
| Сессии путаются | кэш на ресурсе ещё включён; включено «Игнорировать файлы cookie» |
| TLS клиента не проходит | CNAME ещё не распространился; на крае стоит сертификат по умолчанию `*.yccdn.cloud.yandex.net`, а не LE на `cdn.example.com` |
| `loft-bench` 404 / пустой mux | не указан `-path /static/v3/build` |

Ограничения края: [источники](https://yandex.cloud/ru/docs/cdn/concepts/origins) (IPv4, 5 с), [обмен с origin](https://yandex.cloud/ru/docs/cdn/concepts/servers-to-origins).
